# ai_road — сегментация карьерной дороги

Консольный Python-проект для выделения дороги на видео и изображения центральной и боковых зон. Обучение выполняется в PyTorch; обработка видео поддерживает PyTorch, ONNX Runtime и OpenVINO на CPU. Графический интерфейс нужен только для ручной разметки и необязательного просмотра видео.

Новая обработка использует прямоугольный вход с сохранением пропорций, ROI, EMA вероятностей, гистерезис и геометрию центральных линий. Исходная LiteRoadNet и режим `legacy` сохранены для сравнений. По умолчанию выбирается `lite_road_net`; переход к `fast_scnn_lite` требует сравнения на размеченных данных и целевом процессоре.

**15 FPS, полный цикл до 66,7 мс и Road IoU около 0,90 являются целями проверки. Их достижение на целевом оборудовании не заявляется.** Репозиторий не содержит обученной на ваших данных модели или независимого карьерного test-набора. Выполненные проверки и оставшиеся условия приемки описаны в [VALIDATION.md](VALIDATION.md).

## Установка

Проверенное локальное окружение использует Python 3.12. Запускайте команды из корня репозитория. В Windows PowerShell:

```powershell
py -3.12 -m venv .venv
./.venv/Scripts/Activate.ps1
python -m pip install --upgrade pip
python -m pip install torch --index-url https://download.pytorch.org/whl/cpu
python -m pip install -r requirements.txt
```

Если активация окружения недоступна, заменяйте `python` в командах на `./.venv/Scripts/python.exe`. Для другой платформы выбирайте подходящий CPU-пакет по [официальной инструкции PyTorch](https://pytorch.org/get-started/locally/). GPU для запуска и обучения не обязателен; все команды ниже используют CPU.

Базовые зависимости: NumPy, OpenCV и PyTorch. Экспорт, квантование и альтернативные backend устанавливаются отдельно:

```powershell
python -m pip install -r requirements-onnx.txt
python -m pip install -r requirements-openvino.txt
```

`requirements-onnx.txt` добавляет ONNX и ONNX Runtime. `requirements-openvino.txt` добавляет OpenVINO. Для тестов нужен pytest:

```powershell
python -m pip install pytest
python -m pytest -q
```

Если необязательные зависимости не установлены, соответствующие backend-тесты могут быть пропущены. Для полной проверки установите оба дополнительных файла зависимостей. `unittest discover` запускает только unittest-часть; полную проверку, включая данные и обучение, выполняет pytest.

## Запуск через меню

```powershell
python app.py
```

Меню вызывает те же CLI-команды и позволяет:

1. Извлечь BMP-кадры и разметить маски.
2. Разделить данные по рейсам.
3. Начать обучение, продолжить его с оптимизатором или загрузить только веса.
4. Обработать видео и запустить benchmark без окна.
5. Оценить модель на независимом test.
6. Экспортировать ONNX и выполнить статическое INT8-квантование.

Камера, расширенные параметры ветвей и сравнение двух моделей доступны через CLI. Справка каждого скрипта открывается с `--help`.

## Подготовка кадров и масок

Один рейс должен целиком принадлежать одной выборке. Разные фрагменты одного рейса нельзя объявлять независимыми группами.

```powershell
python prepare.py videos/trip01.mp4 data/trip01/images --group trip01 --every 10
python annotate.py data/trip01/images data/trip01/masks
```

`prepare.py` сохраняет каждый десятый кадр в файлы вида `trip01_frame_000000.bmp` и записывает `trip01.frames.json` с происхождением. `--every` задает шаг, `--group` — префикс; без него используется имя исходного видео. Повторное извлечение той же группы в ту же папку отклоняется, чтобы не перезаписать кадры.

Разметчик читает BMP и сохраняет маски `<имя_кадра>_mask.bmp`. Маска имеет исходные размеры кадра, значения 0 и 255. Существующая маска открывается для редактирования.

| Действие | Управление |
|---|---|
| Добавить вершину полигона | Левая кнопка мыши |
| Завершить полигон | Правая кнопка или Enter |
| Добавлять области дороги | `a` |
| Вычитать области | `d` |
| Сделать полностью черную маску | `b` |
| Отменить вершину или последнее изменение | `u` |
| Сбросить незавершенные вершины | `c` |
| Сохранить и перейти к следующему кадру | `s` |
| Подтвердить перезапись существующей маски | Повторное `s` |
| Следующий / предыдущий кадр | `n` / `p` |
| Выйти | `q` или Esc |

Полупрозрачное наложение помогает проверить границы. Можно последовательно добавить и вычесть несколько полигонов. При переходе с несохраненными изменениями действие нужно повторить для отказа от них; при выходе также показывается предупреждение.

Включайте трудные отрицательные примеры: отвалы, стены, площадки, тени, небо, капот, технику, соседние дороги и кадры без дороги. Для кадра без дороги сохраните черную маску.

## Разделение по рейсам и аудит данных

Шаблон [examples/groups.example.json](examples/groups.example.json) содержит 20 условных рейсов. Замените их реальными группами и папками; сами изображения в шаблон не входят. Пути в этом JSON отсчитываются от папки, в которой лежит JSON. Поэтому `../data/trip01/images` в файле под `examples/` указывает на `data/trip01/images` в корне проекта.

```powershell
python data_tools.py split --groups examples/groups.example.json --output splits.json --seed 42
python data_tools.py validate splits.json --output reports/data_audit.json
```

Формат описания источников:

```json
{
  "groups": [
    {
      "group": "trip01",
      "images_dir": "../data/trip01/images",
      "masks_dir": "../data/trip01/masks"
    }
  ]
}
```

Одна запись выше иллюстрирует формат; для разбиения нужны как минимум три независимые группы. Для фрагментов одного рейса задавайте одинаковое поле `group`, даже если папки разные. Порядок или названия соседних кадров не используются для определения независимости.

Разбиение приближает **70/15/15 по количеству групп**, с округлением и минимум одной группой в каждой выборке. Для 20 групп это 14/3/3; для трех — 1/1/1. Доли кадров могут отличаться, поскольку длина рейсов различается. Случайное перемешивание отдельных кадров между выборками отсутствует.

Полученный manifest имеет схему:

```json
{
  "version": 1,
  "splits": {
    "train": [{"image": "path/to/frame.bmp", "mask": "path/to/frame_mask.bmp", "group": "trip01"}],
    "validation": [{"image": "path/to/other.bmp", "mask": "path/to/other_mask.bmp", "group": "trip02"}],
    "test": [{"image": "path/to/test.bmp", "mask": "path/to/test_mask.bmp", "group": "trip03"}]
  }
}
```

Относительные пути внутри manifest разрешаются относительно самого manifest. Генератор записывает абсолютные пути.

Аудит проверяет:

- Наличие, читаемость и одинаковые размеры пары; одноканальные бинарные маски 0/255 либо 0/1.
- Пропущенные и лишние маски при обнаружении пар, неоднозначные имена, повторное использование путей.
- Отсутствие одной группы в нескольких выборках.
- Отсутствие одинаковых декодированных изображений в разных выборках, включая копии с другим именем или кодированием.
- **Наличие хотя бы одного кадра без дороги в каждой из train, validation и test.**

Отсутствие отрицательных кадров — ошибка аудита. Увеличьте разнообразие исходных групп; при генерации допустимо выбрать другой `--seed`, но нельзя переносить соседние кадры одного рейса между выборками. Хеш-проверка находит точные копии изображения; корректность идентификаторов рейсов остается обязанностью подготовки данных.

## Обучение двух архитектур

Стартовый вход — **256×144**, экономичный вариант — **224×128**. Размеры должны быть положительными и кратными 16. Из верхней части кадра по умолчанию исключаются 20% (`--roi-top 0.20`); оставшийся ROI масштабируется пропорционально и дополняется letterbox.

```powershell
python train.py --manifest splits.json --architecture lite_road_net --input-width 256 --input-height 144 --roi-top 0.20 --epochs 50 --batch-size 8 --device cpu --threads 1 --output models/lite.pth
python train.py --manifest splits.json --architecture fast_scnn_lite --input-width 256 --input-height 144 --roi-top 0.20 --epochs 50 --batch-size 8 --device cpu --threads 1 --output models/fast.pth
```

Экономичный профиль обучается или дообучается отдельно:

```powershell
python train.py --manifest splits.json --architecture lite_road_net --input-width 224 --input-height 128 --roi-top 0.20 --epochs 50 --batch-size 8 --output models/lite_224.pth
```

LiteRoadNet сохраняет прежнюю структуру весов и содержит 19 233 параметра. FastSCNNLite добавляет быстрый downsampling, bottleneck-блоки, контекст и объединение признаков. Наличие второй архитектуры само по себе не означает улучшение точности или скорости.

Обучение применяет BCE + Dice loss. Средний loss взвешивается по числу примеров в batch, включая неполный последний batch. Валидация вычисляет IoU, Dice/F1, precision, recall, Boundary IoU и частоту ложных срабатываний на кадрах без дороги. Лучший checkpoint выбирается по **validation IoU**.

Аугментации применяются только к train: горизонтальное отражение, небольшие повороты и масштабирование, перспектива, crop, яркость, контраст, gamma, цветовые сдвиги, Gaussian/motion blur, шум, туман/пыль, тени, засветка и JPEG-артефакты. Геометрические преобразования изображения и маски согласованы; вертикального отражения нет.

Дополнительные параметры обучения: `--lr`, `--weight-decay`, `--workers`, `--seed`, `--threshold` и `--boundary-ratio`. Порог по умолчанию 0,55, ширина полосы Boundary IoU — 0,02 от диагонали. Настраивайте их по validation.

При `--output models/lite.pth` создаются:

| Файл | Содержимое |
|---|---|
| `models/lite.pth` | Лучшие веса по validation IoU и состояние той эпохи |
| `models/lite.last.pth` | Последние веса, оптимизатор, завершенная эпоха и лучший результат |
| `models/lite.history.json` | История loss/метрик и аудит набора данных |

Checkpoint содержит `model`, `architecture`, `input_width`, `input_height`, `roi_top`, `class_names`, `epoch`, `optimizer`, `best_validation_score` и `preprocess_version=1`. Также сохраняются параметры метрик, происхождение train/validation и отпечаток данных.

Метрики в ходе обучения рассчитываются на входном canvas модели. Полноценную оценку в исходных координатах выполняет `evaluate.py`; значение validation IoU из истории не следует подменять итоговым full-frame test IoU.

## Resume, finetune и старые checkpoint

Продолжить обучение до суммарных 80 эпох:

```powershell
python train.py --manifest splits.json --resume models/lite.last.pth --epochs 80 --batch-size 8 --output models/lite.pth
```

`--resume` восстанавливает веса, оптимизатор, число завершенных эпох и лучший validation IoU. Если сохранена эпоха 50, `--epochs 80` выполнит еще 30 эпох. Manifest должен иметь тот же отпечаток; архитектура, вход, ROI и параметры валидационных метрик должны совпадать с checkpoint. При продолжении штатно использовать тот же `--output`.

Загрузить только веса и начать новый цикл:

```powershell
python train.py --manifest splits.json --finetune models/lite.pth --epochs 20 --lr 0.0001 --output models/lite_finetuned.pth
```

`--finetune` создает новый оптимизатор, начинает счетчик эпох заново и допускает новые параметры предобработки. Происхождение предобучения сохраняется: пересечение ранее обучавших модель кадров с новым validation/test отклоняется.

Старые checkpoint с `image_size` загружаются backend как `preprocess_version=0`: прежняя квадратная деформация и ROI 0. Это нужно для воспроизводимого сравнения старой модели. Для перехода к прямоугольному входу используйте дообучение:

```powershell
python train.py --manifest splits.json --finetune models/old_lite.pth --input-width 256 --input-height 144 --roi-top 0.20 --epochs 20 --output models/lite_migrated.pth
```

Старый checkpoint без оптимизатора нельзя продолжить через `--resume`. Если происхождение старых весов неизвестно, новый checkpoint сохраняет признак неполной provenance; само дообучение не доказывает независимость старых данных.

## Независимая оценка качества

Сначала определите порог по validation, затем зафиксируйте его до просмотра test:

```powershell
python evaluate.py models/lite.pth --manifest splits.json --split validation --threshold 0.55 --output reports/lite_validation.json
python evaluate.py models/lite.pth --manifest splits.json --split test --threshold 0.55 --output reports/lite_test.json
```

Если `--threshold` и `--boundary-ratio` не переданы, используются сохраненные значения; для старых моделей — 0,55 и 0,02. Изменение порогов после изучения test превращает этот набор в источник настройки и требует нового независимого теста.

`evaluate.py` восстанавливает предсказание в **полный исходный кадр**. Область выше ROI считается предсказанным фоном; настоящая дорога в этой области учитывается как пропуск. Это оценка сегментации модели при одном пороге, без EMA и геометрии; устойчивость зон и ветвей проверяется отдельно на последовательностях.

Определения метрик:

- IoU, Dice/F1, precision и recall агрегируются по пикселям набора.
- Boundary IoU использует внутреннюю полосу границы: `max(1, round(boundary_ratio × диагональ_кадра))` пикселей.
- `no_road_pixel_fpr` — доля ложных road-пикселей на полностью отрицательных кадрах.
- `no_road_frame_fpr` — доля отрицательных кадров с хотя бы одним ложным road-пикселем.
- Совпадение пустых масок дает IoU/Dice/Boundary IoU 1; при пустом знаменателе precision/recall также принимается 1.

Оценка проверяет manifest и происхождение checkpoint. Test не должен пересекаться с train, validation или калибровочными данными модели. `--allow-unverified-provenance` разрешает отдельно помеченную оценку старых весов без полного происхождения; известное пересечение данных эта опция не разрешает.

Сравнить архитектуры на одинаковых кадрах:

```powershell
python evaluate.py models/lite.pth --manifest splits.json --compare models/fast.pth --compare-backend pytorch --threshold 0.55 --output reports/architecture_comparison.json
```

Отчет содержит обе группы метрик, разницу IoU/Boundary IoU, размер артефакта, median/p95 и FPS инференса. Для второй модели используется тот же порог и определение Boundary IoU. `--device cpu`, `--threads 1` и `--warmup 30` задают условия замера; warmup здесь — предварительные повторные запуски на первом изображении, все изображения набора участвуют в метриках.

`analysis_latency` включает декодирование изображения, предобработку, инференс и восстановление координат. Она исключает метрики, отрисовку и кодирование видео и не заменяет benchmark полного видеоконвейера.

## Экспорт ONNX и OpenVINO

```powershell
python export.py --checkpoint models/lite.pth --output models/lite.onnx --check --check-manifest splits.json --report reports/lite_export.json
python export.py --checkpoint models/fast.pth --output models/fast.onnx --check --check-backend openvino --check-manifest splits.json --report reports/fast_openvino_parity.json
```

Экспорт создает статический ONNX с batch=1, входом NCHW float32 и выходными logits. Поддерживаются обе архитектуры. OpenVINO читает тот же ONNX через `--backend openvino`; отдельный экспорт в XML для этого не требуется.

Рядом создается обязательный `<model>.onnx.json`: архитектура, размеры, ROI, версия предобработки, происхождение и SHA256 модели. Переносите ONNX вместе с этим файлом. Несовпадение SHA256 или отсутствие metadata приводит к ошибке.

`--check-manifest` проверяет численное соответствие на кадрах test из проверенного manifest. Вместо него можно передать `--check-images path1.bmp path2.bmp`. Проверка `--check` без изображений использует синтетические входы — это smoke-проверка экспорта, а не доказательство качества на дорожных данных.

Сравниваются вероятности PyTorch и выбранного backend с `--atol 0.00001` и `--rtol 0.0001`. Несоответствие допуску завершает экспортную проверку ошибкой. Численная близость не заменяет IoU на размеченных кадрах.

## Статическое INT8 и контроль ухудшения

Для калибровки нужны **200–500 уникальных репрезентативных кадров только из train**:

```powershell
python quantize.py --model models/lite.onnx --manifest splits.json --output models/lite.int8.onnx --samples 200 --seed 42 --threads 1 --report reports/lite_calibration.json
```

Выборка распределяется по train-группам; validation и test не используются. Недостаток уникальных кадров вызывает ошибку. Репрезентативность по пыли, освещению, покрытию и отрицательным примерам нужно обеспечить при подготовке train.

Квантование использует статический QDQ INT8 для Conv; остальные операции графа могут оставаться float. Создаются INT8 ONNX, его JSON metadata и отчет о калибровке. Метаданные сохраняют группы, хеши и отпечаток калибровочных данных. Численный drift на калибровке не является оценкой точности.

Сравнение FP32 и INT8 на одном независимом test:

```powershell
python evaluate.py models/lite.onnx --backend onnxruntime --manifest splits.json --compare models/lite.int8.onnx --compare-backend onnxruntime --max-iou-drop 0.02 --output reports/lite_fp32_int8.json
```

`--max-iou-drop 0.02` означает максимум **2 процентных пункта IoU**, а не 2% относительного значения. Отчет содержит IoU, Boundary IoU, FPS, median/p95, размер моделей и разницу результатов. При превышении допуска для INT8 отчет сохраняется, а CLI завершается с кодом 2. Для других сравнений такой же контроль можно включить через `--enforce-iou-drop`.

При недопустимом ухудшении INT8 не принимается: потребуется отдельное обучение с учетом квантования (QAT), повторный экспорт и повторная независимая проверка. Автоматический QAT в текущем CLI не реализован и без реального измеренного ухудшения не заявляется выполненным. Успешная статическая калибровка сама по себе не означает прохождение приемки.

## Обработка видео

```powershell
python infer.py videos/trip_test.mp4 models/lite.pth --backend pytorch --output results/road_zones.mp4 --report reports/video_pytorch.json
python infer.py videos/trip_test.mp4 models/lite.int8.onnx --backend onnxruntime --output results/road_zones_int8.mp4 --report reports/video_int8.json --no-display
python infer.py videos/trip_test.mp4 models/lite.onnx --backend openvino --output results/road_zones_openvino.mp4 --report reports/video_openvino.json --no-display
```

Размер входа и ROI читаются из модели. Если передать `--input-width`, `--input-height` или `--roi-top`, значение должно совпасть с metadata. Нельзя переключить обученную модель 256×144 на 224×128 простой заменой аргументов инференса.

Цвета визуализации:

| Цвет | Значение |
|---|---|
| Красный | Область вне подтвержденной дороги |
| Зеленый | Центральный коридор |
| Желтый | Боковые зоны подтвержденной дороги |
| Белый | Внутренние границы зон |
| Синий | Внешний контур дороги |

`--left 0.15 --center 0.70 --right 0.15` задают доли зон, сумма должна быть 1. Центральный коридор в centerline-режиме строится относительно центральной линии; обе боковые зоны имеют одинаковый цвет.

Связные компоненты, очистка, скелет, distance transform, поиск ветвей и построение зон выполняются на **малой маске ROI без letterbox-полей**. До размеров видео увеличиваются готовая маска и цветная разметка. Зеленые и желтые зоны ограничены подтвержденной маской **после геометрической очистки**, включая допустимое заполнение небольших разрывов.

Параметры временной обработки:

| Аргумент | Значение по умолчанию | Смысл |
|---|---:|---|
| `--temporal-mode` | `ema` | `ema`, историческое голосование `legacy` или `none` |
| `--temporal-alpha` | 0.70 | Вес текущей вероятности в EMA |
| `--low-threshold` | 0.40 | Возможная дорога, связанная с уверенной областью |
| `--high-threshold` | 0.65 | Уверенная дорога |
| `--scene-threshold` | 0.25 | Порог изменения уменьшенного изображения для сброса истории |
| `--threshold` | 0.55 | Порог только исторического голосования |
| `--temporal-window` | 5 | Окно исторического голосования |
| `--min-confirmed-frames` | 4 | Подтверждения в историческом голосовании |

EMA: `smoothed = alpha × current + (1 − alpha) × previous`. В режиме `none` временного усреднения нет, но гистерезис сохраняется. История сбрасывается при новом источнике, изменении размеров или резкой смене сцены. Пороги гистерезиса и временные параметры выбирайте по validation-видео.

`--geometry centerline` используется по умолчанию; `--geometry legacy` включает прежнее построчное деление для сравнения. Новый алгоритм строит граф скелета, удаляет короткие отростки, оценивает локальную ширину через distance transform и ведет коридоры вдоль поворотов.

| Аргумент ветвей | По умолчанию | Единицы |
|---|---:|---|
| `--corridor-mode` | `all` | Все подтвержденные ветви или выбранная основная `main` |
| `--min-branch-length` | 0.12 | Доля высоты малого ROI |
| `--min-branch-width` | 0.05 | Доля ширины малого ROI |
| `--min-branch-angle` | 25 | Градусы |
| `--min-branch-area` | 0.002 | Доля площади малого ROI |
| `--branch-confirm-frames` | 3 | Последовательные кадры подтверждения |
| `--branch-missing-frames` | 2 | Допустимые пропуски до удаления |

Ветви проходят состояния `candidate → confirmed → missing → removed`. Основная линия учитывает вход дороги в нижнюю область и продолжение направления. `all` показывает варианты дороги, `main` — выбранную алгоритмом линию; это визуальная гипотеза, а не навигационный маршрут или команда управления.

## Файл, камера и очереди

Чтение, анализ и запись разделены двумя очередями по 2 кадра. `--queue-size` допускает 2 или 3.

- `--source-mode file`: очереди блокируют более быстрый этап; кадры намеренно не отбрасываются. После нормального завершения проверяются счетчики чтения/обработки/записи и FPS/число кадров выходного файла.
- `--source-mode camera`: устаревшие кадры во входной очереди могут отбрасываться; отчет содержит `frames_dropped`. Это ограничивает накопление задержки.
- `--output` необязателен. Без него видео не записывается. `--no-display` отключает окно, `q` в окне прерывает обработку.
- Смена разрешения внутри открытого источника требует нового выходного файла и завершает текущий запуск ошибкой.
- Звук не копируется. OpenCV записывает MP4 с частотой из метаданных источника; временные метки переменного FPS не сохраняются как отдельный поток.

Пример камеры:

```powershell
python infer.py 0 models/lite.pth --source-mode camera --camera-fps 30 --queue-size 2 --report reports/camera.json
```

`--camera-fps` задает частоту камеры явно, если устройство ее не сообщает. Без заданной выходной записи частота все равно используется в отчете. Прерванный пользователем файл помечается `interrupted` и не считается полным результатом.

## Benchmark на целевом CPU

Используйте реальные видео нужного разрешения, тот же кодек вывода и заранее зафиксированное число потоков:

```powershell
python infer.py videos/trip_test.mp4 models/lite.int8.onnx --backend onnxruntime --device cpu --threads 1 --source-mode file --queue-size 2 --output results/benchmark.mp4 --report reports/target_cpu_benchmark.json --warmup 30 --fps-window 30 --no-display
```

Отчет включает mean, median и p95 в миллисекундах для `read`, `prepare`, `inference`, `temporal`, `geometry`, `render`, `write` и `total`. Первые 30 завершенных кадров исключаются из статистики, но сохраняются в выходном видео.

`total` измеряется **от начала чтения кадра до завершения записи и включает ожидания обеих очередей**. Времена отдельных этапов показывают их собственную работу. Из-за параллельного выполнения сумма этапов, обратная средняя задержка кадра и производительность конвейера — разные показатели.

`average_fps` рассчитывается по интервалам завершения после прогрева. `minimum_sustained_fps` — минимум по скользящим окнам из 30 завершенных кадров. Для него нужны минимум 30 измеренных кадров после прогрева; иначе поле равно `null`. Параметры окна и прогрева задаются явно.

Сравнивайте FP32/INT8 и архитектуры на одинаковых условиях: CPU, потоки, разрешение/кодек, входная модель, ROI, геометрия, вывод и видео. Сохраните JSON и сведения об оборудовании. Предел p95 полного времени должен быть согласован отдельно; высокая частота завершения кадров сама по себе не подтверждает требуемую задержку.

## Проверки и границы результата

```powershell
python -m pytest -q
```

Тесты охватывают геометрию прямых, диагоналей, поворотов и перекрестков, шумовые компоненты, разрывы, частичные перекрытия, подтверждение ветвей, ROI, временные сбросы, сохранение файловых кадров, данные без утечки, метрики, resume/finetune и соответствие backend. Синтетические формы проверяют алгоритмические свойства; они не заменяют тест на независимых карьерных видео.

Для завершения измеримой приемки нужны целевой процессор, размеченные независимые рейсы, обученные веса, репрезентативная калибровка и согласованный p95. Текущее состояние подтверждается [VALIDATION.md](VALIDATION.md).

Проект предназначен для визуального анализа. Применение в автономном управлении потребует отдельной проверки отказов, калибровки камеры, оценки расстояний и независимых средств контроля.
